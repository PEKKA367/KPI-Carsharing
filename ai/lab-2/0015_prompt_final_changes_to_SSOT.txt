# SSOT.md (Завдання 2: Вимоги та Use Cases)

## Блок 1. Специфікація (spec.md)

### План

1. Створити файл `spec.md`.
2. Описати намір (що проєктуємо) та сутності/кроки.
3. Описати акторів та їхні цілі на основі аналізу домену.
4. Описати вимірювані критерії прийняття, які ШІ має виконати й самоперевірити.

### Обмеження

* Обсяг: до 1 сторінки.
* Пишеться власноруч (ШІ може лише ставити уточнювальні запитання під час "Інтерв'ю").
* Система каршерінгу НЕ є актором.
* Зовнішня система (напр., платіжний шлюз) — актор ЛИШЕ якщо сама ініціює взаємодію. Таймер, worker, шлюз "бо потрібен" — це деталі реалізації, а не актори.

### Паралельні процеси

## Блок 2. Use-case діаграма

### План

1. Згенерувати Use-case діаграму (інструмент: PlantUML або Mermaid).
2. Нанести акторів, варіанти використання та System Boundary (межі системи).

### Обмеження

* UC (Use Case) = потреба актора. Дія системи («перевірити роль», «валідувати») — це НЕ UC.
* Абстрактний use case, який не реалізує жоден актор — помилка.
* Мають бути використані зв'язки:
* `include` — лише для невід'ємних підкроків (напр., зміна оплати включає повторну автентифікацію). Передумови й логічні залежності стрілками не малюються.
* `extend` — для варіацій основного сценарію (напр., застосувати промокод).
* `узагальнення акторів` — нащадок отримує доступ до всього, що вміє базовий актор.


* Стрілки: незаповнений наконечник між акторами, заповнений — між use case.
* System Boundary: обов'язково показати, у якій системі існує use case (напр., каршерінг vs платіжний процесор).

### Паралельні процеси

* Перевірити якість рендеру. Якщо PlantUML дає поганий лейаут, переробити (можна в draw.io).

## Блок 3. Сценарії використання (Gherkin)

### План

1. Обрати ОДИН найскладніший прецедент (UC) з діаграми.
2. Розписати 2-3+ сценарії для цього UC у синтаксисі Gherkin.
3. Включити граничні випадки та навмисні ускладнення доступу (якщо функціонал небажаний або застарілий).

### Обмеження

* Мова: Українська (`# language: uk`) АБО Англійська. Змішувати заборонено.
* Окремого розділу «User stories» немає. User story пишеться ОДРАЗУ у форматі Gherkin.
* **Синтаксис Gherkin:**
* Базова структура: `Feature` ➔ `Background` (передумова) ➔ `Scenario` ➔ `Given` / `When` / `Then` (доповнені `And`, `But`, `*`).
* `Rule` (Правило) — використовується для універсальних бізнес-правил. Обов'язково ілюструється хоча б одним `Example` (Прикладом). Кроки, покриті правилом, у сценаріях не дублюються.
* `Scenario Outline` (Структура сценарію) — використовується для однотипних сценаріїв. Обов'язково супроводжується таблицею `Examples` (Приклади) для фіксації граничних випадків.


* Теги (напр., `@billing`) та коментарі (`#`) використовуються за потреби.

## Блок 4. Функціональні вимоги (EARS)

### План

1. Написати функціональні вимоги в синтаксисі EARS.
2. Провести аналіз конфліктів (перевірити, чи вимоги не суперечать одна одній).

### Обмеження

* Використовується **Підхід 2 (Уточнення)**: EARS-вимоги описують ЛИШЕ те, що неможливо виразити в Gherkin (технічні деталі: токени, правила retry, ліміти, поведінка при збоях).
* EARS-вимоги пишуться ЛИШЕ для обраних у Блоці 3 сценаріїв.
* **Шаблон EARS:** `[ЯКЩО | КОЛИ <передумова>,] <актор | система> МОЖЕ | ПОВИННА <опис дії> [<уточнення>]`.
* **Правило написання:** Службові слова (ЯКЩО, КОЛИ, ПОКИ, МОЖЕ, ПОВИННА, ТО) обов'язково пишуться ВЕЛИКИМИ літерами.
* Вимога не має допускати жодного альтернативного прочитання (слова "нормальне", "основні" — дефекти).

## Блок 5. Нефункціональні вимоги (NFR) та Межі

### План

1. Написати Нефункціональні вимоги (NFR) окремим блоком.
2. Написати розділ «Поза обсягом» (Out of scope): що свідомо не робиться і чому.

### Обмеження

* Без NFR робота не зараховується.
* Кожна NFR повинна мати числа й межі (навантаження, час відгуку, з яких пристроїв, мова інтерфейсу тощо).
* Категорії NFR: зручність, продуктивність, надійність, безпека, залежність від постачальника (vendor lock-in).
* NFR НЕ наносяться на UC-діаграму і НЕ трасуються в матриці.
* **Правило навантаження:** Заборонено писати верхню межу (напр., "до 3000"). Треба писати нижню межу ("щонайменше 3000") І обов'язково описувати "поведінку понад межу" (що робить система, якщо ліміт перевищено — напр., повільніша відповідь, але збереження всіх транзакцій).
* Критерії прийняття мають бути вимірюваними (не "зручний інтерфейс", а "90% фокус-групи оцінюють як приємний").
