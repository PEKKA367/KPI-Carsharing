## Лабораторна 2
## Частина 1: Актори та Use-case діаграма

### Намір
Згенерувати діаграму варіантів використання (Use Case) для описаних нижче акторів каршерінгу, щоб візуалізувати їхні базові потреби та межі системи.

### Актори та їні цілі
1. **
Клієнт (Водій) та його ціль:** Знайти найближче вільне авто, забронювати його, розблокувати двері, здійснити поїздку та успішно її завершити (із закриттям дверей та оплатою).
2. **Адміністратор та його ціль:** Керувати автопарком (додавати нові авто, знімати їх з лінії для ремонту) та налаштовувати дозволені паркувальні зони на карті.
3. **GPS-трекер (вбудований у машину):** Безперебійно передавати актуальну телеметрію на сервер.

### Критерії прийняття (Частина 2)
1.
Діаграма має бути написана мовою розмітки Mermaid.
2. На діайграмі обов'язково має бути рамка System Boundary (Межа системи), всередині якої знаходяться варіанти використання (Use Cases), а зовні — актори.
3. Обов'язково нанести всіх зазначених акторів описаних вище
4. Варіанти використання (овали) мають відображати потреби акторів, а не внутрішні дії системи (наприклад, "Орендувати авто", а не "Перевірити баланс").
5. На діаграмі мають бути використані зв'язки include (для обов'язкових підкроків, напр., "Автентифікація") та extend (для опціональних розширень, напр., "Застосувати промокод").



Відповідь ШІ:
Ось готовий код твоєї діаграми. Вона ідеально відповідає всім описаним тобою критеріям прийняття.

Для відображення на GitHub просто скопіюй цей блок у свій файл.

```mermaid
flowchart LR
    %% Актори (винесені за межі системи)
    Client((Клієнт))
    Admin((Адміністратор))
    GPS((GPS-трекер))

    %% Межа системи (System Boundary)
    subgraph System [Мережа Каршерінгу]
        direction TB

        %% Варіанти використання (Потреби акторів)
        UC_Rent([Орендувати авто])
        UC_Promo([Застосувати промокод])
        UC_Auth([Пройти автентифікацію])

        UC_Fleet([Керувати автопарком])
        UC_Zones([Налаштувати паркувальні зони])

        UC_Telemetry([Передати телеметрію])
    end

    %% Базові зв'язки акторів із варіантами використання
    Client --> UC_Rent
    Admin --> UC_Fleet
    Admin --> UC_Zones
    GPS --> UC_Telemetry

    %% Зв'язки include (обов'язкові підкроки)
    %% Стрілка йде ВІД базового прецеденту ДО обов'язкового кроку
    UC_Rent -. "«include»" .-> UC_Auth
    UC_Fleet -. "«include»" .-> UC_Auth
    UC_Zones -. "«include»" .-> UC_Auth

    %% Зв'язки extend (опціональні розширення)
    %% Стрілка йде ВІД опціонального кроку ДО базового прецеденту (правило UML)
    UC_Promo -. "«extend»" .-> UC_Rent

```

**Як виконано твої критерії (DoD):**

1. **Mermaid синтаксис:** Використано структуру `flowchart LR` (зліва направо), яка найкраще підходить для Use Case діаграм. Актори зроблені круглими вузлами `(( ))`, а Use Cases — овалами `([ ])`.
2. **System Boundary:** Створено за допомогою `subgraph System`. Усі актори лежать зовні, а бізнес-логіка (овали) інкапсульована всередині.
3. **Усі актори нанесені:** Клієнт, Адміністратор та GPS-трекер ініціюють взаємодію кожен зі свого боку.
4. **Потреби, а не дії:** Усі Use Cases сформульовані як бізнес-цілі (Орендувати, Керувати, Налаштувати, Передати), що відповідає рівню абстракції цієї діаграми. Жодних системних підкроків на кшталт "Зберегти в базу" немає.
5. **Include та Extend:**
* `include`: І Клієнт (при оренді), і Адмін (при вході в панель) зобов'язані авторизуватися. Базові Use Cases вказують на `UC_Auth`.
* `extend`: Промокод застосовується лише за бажанням. За правилами стандарту UML, стрілка `extend` вказує **від** розширення (`UC_Promo`) **до** базового прецеденту (`UC_Rent`).
