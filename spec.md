# Специфікація системи: Мережа каршерінгу

## Частина 1: Доменна модель (ER)

### Намір
Побудувати концептуальну модель сутностей та зв'язків (ERD) для платформи короткострокової оренди автомобілів, щоб відобразити базову бізнес-логіку системи без деталей фізичної реалізації бази даних.

### Сутності та атрибути
1. **Client (Клієнт):** id (PK), phone, email, license_number, registration_date.
2. **Vehicle (Автомобіль):** id (PK), license_plate, model, float fuel_level, status.
3. **ParkingZone (Паркувальна зона):** id (PK), location_name, max_capacity.
4. **RentalSession (Сеанс оренди):** id (PK), start_time, end_time.
5. **Payment (Платіж):** id (PK), numeric amount, status, timestamp.

### Зв'язки (Бізнес-правила)
- Один `Client` може мати багато `RentalSession` (історія поїздок), але `RentalSession` завжди належить лише одному `Client`.
- Один `Vehicle` може мати багато `RentalSession`, але конкретний `RentalSession` стосується лише одного `Vehicle`.
- Одна `ParkingZone` може містити багато `Vehicle`, але `Vehicle` (у стані очікування) прикріплюється лише до однієї `ParkingZone`.
- Один `RentalSession` може породжувати лише один `Payment` (транзакцію), а кожен `Payment` суворо прив'язаний до конкретного `RentalSession`.

### Критерії прийняття (Частина 1)
1. Модель повинна бути приведена до 3-ї нормальної форми (3NF).
2. Усі первинні ключі (PK) повинні мати назву `id` та тип даних `uuid`.
3. Зв'язки між сутностями мають бути показані концептуально (через кардинальність), без використання суто фізичних сполучних (асоціативних) таблиць.
4. Результат має бути згенерований у декларативному синтаксисі Mermaid (тип `erDiagram`).
5. Текст зв'язків у синтаксисі Mermaid має бути англійською та без лапок.

## Частина 2: Вимоги та Сценарії використання (Use Cases)

### Намір
Визначити поведінку системи каршерінгу: визначити акторів, зафіксувати їхні можливості та правила взаємодії, а також протрасувати зв'язки між функціональними вимогами та конкретними сценаріями використання.

### Актори та їхні цілі
1. **Клієнт (Client) [Людина]:**
    - *Мета:* Знайти доступне авто, успішно його орендувати та коректно завершити поїздку.
2. **Платіжний шлюз (Payment Gateway) [Зовнішня система]:**
    - *Мета:* Отримати від нашої системи запит на списання коштів за оренду та повернути статус транзакції (успіх/відмова).

### Критерії прийняття (Частина 2)
1. Визначено щонайменше 2 типи акторів (людина + зовнішня система/сервіс).
2. Вимоги сформульовані у напівстандартизованому форматі EARS без двозначностей.
3. Описані сценарії використання у форматі Gherkin (Given/When/Then).
4. Побудована Use Case діаграма (Mermaid) з використанням зв'язків `include` та `extend` та генералізацією.
5. Складена матриця трасування (вимоги ↔ сценарії) зі зв'язками "багато-до-багатьох" та щонайменше однією явно непокритою вимогою з поясненням.
