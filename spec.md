# Специфікація системи: Мережа каршерінгу

## Лабораторна 1
## Частина 1: Доменна модель (ER)

### Намір
Побудувати концептуальну модель сутностей та зв'язків (ERD) для платформи короткострокової оренди автомобілів, щоб відобразити базову бізнес-логіку системи без деталей фізичної реалізації бази даних.

### Сутності та атрибути
1. **Client (Клієнт):** id (PK), phone, email, license_number, registration_date.
2. **Vehicle (Автомобіль):** id (PK), license_plate, model, float fuel_level, status.
3. **ParkingZone (Паркувальна зона):** id (PK), location_name, max_capacity.
4. **RentalSession (Сеанс оренди):** id (PK), start_time, end_time.
5. **Payment (Платіж):** id (PK), numeric amount, status, timestamp.

### Зв'язки (Бізнес-правила)
- Один `Client` може мати багато `RentalSession` (історія поїздок), але `RentalSession` завжди належить лише одному `Client`.
- Один `Vehicle` може мати багато `RentalSession`, але конкретний `RentalSession` стосується лише одного `Vehicle`.
- Одна `ParkingZone` може містити багато `Vehicle`, але `Vehicle` (у стані очікування) прикріплюється лише до однієї `ParkingZone`.
- Один `RentalSession` може породжувати лише один `Payment` (транзакцію), а кожен `Payment` суворо прив'язаний до конкретного `RentalSession`.

### Критерії прийняття (Частина 1)
1. Модель повинна бути приведена до 3-ї нормальної форми (3NF).
2. Усі первинні ключі (PK) повинні мати назву `id` та тип даних `uuid`.
3. Зв'язки між сутностями мають бути показані концептуально (через кардинальність), без використання суто фізичних сполучних (асоціативних) таблиць.
4. Результат має бути згенерований у декларативному синтаксисі Mermaid (тип `erDiagram`).
5. Текст зв'язків у синтаксисі Mermaid має бути англійською та без лапок.

## Лабораторна 2
## Частина 1: Актори та Use-case діаграма

### Намір
Згенерувати діаграму варіантів використання (Use Case) для описаних нижче акторів каршерінгу, щоб візуалізувати їхні базові потреби та межі системи.

### Актори та їні цілі
1. **Клієнт (Водій) та його ціль:** Знайти найближче вільне авто, забронювати його, розблокувати двері, здійснити поїздку та успішно її завершити (із закриттям дверей та оплатою).
2. **Адміністратор та його ціль:** Керувати автопарком (додавати нові авто, знімати їх з лінії для ремонту) та налаштовувати дозволені паркувальні зони на карті.
3. **GPS-трекер (вбудований у машину):** Безперебійно передавати актуальну телеметрію на сервер.

### Критерії прийняття
1. Діаграма має бути написана мовою розмітки Mermaid.
2. На діайграмі обов'язково має бути рамка System Boundary (Межа системи), всередині якої знаходяться варіанти використання (Use Cases), а зовні — актори.
3. Обов'язково нанести всіх зазначених акторів описаних вище
4. Варіанти використання (овали) мають відображати потреби акторів, а не внутрішні дії системи (наприклад, "Орендувати авто", а не "Перевірити баланс").
5. На діаграмі мають бути використані зв'язки include (для обов'язкових підкроків, напр., "Автентифікація") та extend (для опціональних розширень, напр., "Застосувати промокод").

## Частина 2: Сценарії використання (Gherkin)

### Намір
Обрати найскладніший Use-case (Оберемо комплекний "Орендувати авто") та описати його поведінку через 10 сценарії мовою Gherkin.

### Критерії прийняття
1. Мова синтаксису виключно українська (навіть для ключових слів WHEN GIVEN тощо) і зазначається на початку через директиву # language: uk.
2. Функціонал це обраний Use-case, під функціоналом має бути User story у форматі хто/що/навіщо? Клієнт приходить у нашу систему для оренди автомобіля щоб дістатись до точки призначення.
3. Так як на Use-case діаграмі Автентифікація була обов'язковою для кожного головного Use-case акторів, то цей блок має бути записай у Background після функціоналу.
4. Мають бути теги для 2 сценаріїв (обов'язково присутній тег @smoke для базової перевірки), а також тег після # language. 
5. 1 правило (граничний випадок, іде найпершим, одразу після Background, містити 2 приклади). Правило забороняє користувачу проїхати без передплати в 200 гривень. Якщо поїздка вийде дешевше, то повернемо кошти. 
6. 1 сценарій з навмисним ускладненням доступу. Відкривати авто без Bluetooth (через мобільний інтернет із ручним вводом VIN-коду). Якщо користувач не бажає чи не може використовувати Bluetooth, то ми просимо ввести останні 10 символів VIN-коду авто в додатку, коли ти близько до машини (перевірка здійснюється GPS координатами телефону та телематики авто). 
7. 2 додаткові стандартні сценарії. Один успішний, коли користувач забронював авто та доїхав до місця призначення, заплатив та завершив оренду. Другий коли користувач не зміг доїхати до місця призначення через збій датчика палива в машині, тоді ми повертаємо йому суму та даємо промокод (рівень палива менше 3л). 
8. У кінці структура сценаріїв з шаблоном та таблицею з прикладами для 5 окремих схожих за контекстом сценаріїв, які фіксують граничні випадки. Після вичерпання передплати в 200 грн кожні 10 хвилин має бути запит до банку про оплату додаткових 100 грн (у нас 1 хв = 10 грн), щоб користувач не викатав просто так увесь бензин. У разі відсутності коштів на картці сума записується в борг користувачеві, що заблокує акаунт для нової оренди. При повторному запуску двигуна блокуємо його лише після паркування / вимкнення запалювання (або переведення коробки в P) при заборгованості. 
9. Щоб не повторювати ключові слова з блоку сценарію Дано Коли Тоді використовувати І, АЛЕ та *. Мінімум по 1 разу використати кожен замінник. 
10. Граничний випадок та навмисне ускладнення доступу краще виділити на початку через коментар з # для кращої читабельності. 
11. Має бути відсутнє дублювання кроків, які вже покриті правилом.
